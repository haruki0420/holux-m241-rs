# レビュー手順

## 発見 → 修正 → 検証の三段構成

指摘した本人に直させず、3 段階をそれぞれ**別のエージェント**が担当する。

| 段階 | 担当 | 入力 | 出力 |
|---|---|---|---|
| 発見 | レビュー担当 | 仕様書・コード・テスト | `ファイル:行` つき指摘リスト |
| 修正 | **別**エージェント | 指摘リスト（事実誤認には異論を残す） | 修正差分 |
| 検証 | **三人目** | 指摘リスト・差分・テスト（**修正者の説明・コミット本文は読まない**） | 合格 / 不合格 |

**検証の合格条件（3 点すべて必須）**: (1) 全指摘が diff で解消（見送りは理由記録）、(2) 無関係な変更・新たな問題なし、(3) `./tools/check.sh` 6/6。欠けたら差し戻し（検証担当は直さない）。

## 発見段階の 2 種類のレビュー（並行・非共有）

| レビュー | 読むもの | 読まないもの | 観点 |
|---|---|---|---|
| 仕様検収 | 仕様書・コード・テスト | 実装者の説明 | 仕様各項目がどのコード・テストで担保されるか（テストなし・過剰実装は指摘、実機必須は未検証分離） |
| 可読性 | コードのみ | **仕様書**・実装者の説明・仕様検収結果 | 初見の他人が説明なしで読めるか（下記 8 観点） |

可読性 8 観点: (1) 名前、(2) 関数の大きさ（1 抽象度・20 行超は理由明確）、(3) コメント（なぜ・定数根拠）、(4) エラー（次の行動が分かる）、(5) テスト名（仕様の文）、(6) 用語の一貫性、(7) 最小の `pub`、(8) 冒頭 3 行のモジュール doc。加えて「消された安全ゲートの理由」「実装を写しただけのテスト」「未検証を検証済みと読ませる記述」は**必ず指摘**する。

- **共通ルール**: レビュー担当はコードを書かない。指摘は `ファイル:行` 必須。重大度は **Must**（マージ不可）/ **Should**（直すか理由記録）/ **Could**（backlog）。
- **統合**: Must が 1 件でもあればマージ不可。同一箇所の競合は可読性を優先。結果は [`10-review-log.md`](10-review-log.md) に記録し、同じ指摘が 3 回出たら lint/テストで塞ぐ。

## Tier 制（レビュー深度）

非テスト行数（`git diff --numstat <base>..HEAD -- ':!**/tests/**' ':!**/*_test.rs'`、inline `#[cfg(test)]` は含める）と危険度で決める。全 Tier で独立セッションと `review-gate` が必須。

| Tier | 対象 | Stage 1 | Stage 2 / 3 | 変異テスト |
|---|---|---|---|---|
| 1 | docs のみ、テストのみ、または非テスト 1–100 行（安全ゲート・未検証主張に触れる場合は Tier 2 以上） | 独立 1 本（仕様検収） | 必要時のみ | 挙動変更時のみ |
| 2 | 通常コード（非テスト 101–300 行、1 モジュール内） | 仕様 + 可読性の 2 本（変更ファイルのみ） | 必須 | 3〜5 件 |
| 3 | 安全-critical（`m241-flash`・プロトコル・ジオタグ EXIF・破壊的経路）は行数不問。または 301 行以上（まず分割検討）・複数モジュール横断 | 2 本（変更ファイル全体 + 仕様検収のみ関係仕様） | 必須・深掘り | 10 件以上 |

既存大型ブランチの扱いは [`08-parallel-work.md`](08-parallel-work.md) 参照。

## Review gate（マージ前 status）

Stage 3 合格後・マージ直前に、**独立レビュアー**が完全 40 桁 head SHA へ `review-gate` status を付与する（著者セッションは付けない。新 push 時は再レビュー必須）。

```bash
python3 tools/review_gate.py <40-char-head-sha> --pr <number> \
  --verdict mergeable --tier <1|2|3> \
  --reviewer "stage3:<session-id>" \
  --review-url "<PRコメントまたは10-review-log.mdのURL>"
```

- `--verdict blocked` は `failure` を付け理由を `--review-url` に残す。`--dry-run` も `gh` で PR の `state`/`head.sha`/`user.login` を照合するため認証とネットワークが必要。
- 技術的限界: branch protection が強制できるのは status の存在まで（write 権限者は偽装可能）。強化には別アカウント＋required approvals または GitHub App が必要。
