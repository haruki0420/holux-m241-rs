# レビュー手順

## 発見 → 修正 → 検証の三段構成

レビューで問題が見つかったとき、**指摘した本人に直させない**。修正は
**指摘したのとは別のエージェント**が行い、その修正は**さらに別のエージェント**が
独立に検証する。三つの段階は、それぞれ別のエージェントが担当する。

| 段階 | 担当 | 入力 | 出力 |
|---|---|---|---|
| 発見 | レビュー担当 | 仕様書・コード・テスト | `ファイル:行` つきの指摘リスト |
| 修正 | 指摘したのとは**別**のエージェント | 指摘リスト | 修正の差分 |
| 検証 | 修正したのとは**別**のエージェント | 指摘リスト、差分、テスト | 合格 / 不合格 |

修正担当は、指摘が事実と違うと思ったら**直さずにそう言う**。黙って従って
誤った変更を入れるより、異論を書いて残すほうがよい。指摘者本人に直させない
理由は、自分が下した判断を同じ前提で読み直してしまうから。検証担当も同じ理由で、
**修正者の説明を読まない**。説明は、悪い修正を言葉で通り抜けさせるための装置になる。

### 検証担当が読むもの

- 指摘リスト（`ファイル:行` と重大度）
- 修正の差分（`git diff` / `git show`）
- テスト（追加・変更されたテストと、その実行結果）

**読まないもの: 修正者の説明。** コミットメッセージの本文も、修正担当が書いた
「なぜこう直したか」の報告も読まない。差分そのものだけを見る。

### 検証の合格条件

3 つすべてを満たしたときだけ合格とする。

1. 指摘がすべて解消している（各指摘の `ファイル:行` に対応する変更が diff にある。
   見送る場合は、見送る理由が指摘リスト側に記録されている）
2. 修正が新たな問題を入れていない（diff に指摘と無関係な変更が無い。
   無関係に見える変更があれば、それが何の指摘に対応するか説明できる）
3. `./tools/check.sh` が 6/6 で通る

1 つでも欠けたら不合格として差し戻す。検証担当は自分で直さない。

## 2 種類のレビュー（発見段階）

実装とは独立した 2 種類のレビューを、**互いの結果を見せずに並行で**走らせる。
片方だけでは足りない理由がある。

| レビュー | 読むもの | 読まないもの | 問い |
|---|---|---|---|
| 仕様検収 | 仕様書、テスト、コード | 実装者の説明 | 仕様の各項目が、コードとテストのどこで担保されているか |
| 可読性レビュー | コードだけ | 仕様書、実装者の説明、仕様検収の結果 | 半年後の他人が、説明なしで読めるか |

## なぜ分けるか

仕様検収だけだと「仕様に合っているから読みやすさは問わない」になる。
可読性レビューだけだと「きれいだが仕様を満たしていない」を見逃す。

そして**仕様書を読ませないことが可読性レビューの条件**である。
仕様を知っていると、コードの不明瞭さを仕様で補って読めてしまい、
初見の読み手が感じる引っかかりが消える。実装者の説明を読ませないのも同じ理由。

## 共通のルール

- レビュー担当は**コードを書き換えない**。指摘だけ返す。
- 2 つのレビューは独立に走らせ、**互いの報告を読む前**に結論を出す。
- 指摘は必ず `ファイル:行` で示す。行が特定できない指摘は「指摘ではない」。
- 重大度は 3 段階。
  - **Must** — 誤動作、データ損失、安全性の後退、仕様違反。マージ前に直す。
  - **Should** — 読み手が誤解する、または保守で事故る。直すか、直さない理由を記録する。
  - **Could** — 好みに近い改善。 backlog に落としてよい。

## 仕様検収

入力: 対象の仕様書（例 `docs/reference/01-da-protocol.md`）、コード、テスト。

1. 仕様書の項目を 1 行ずつ列挙する。
2. 各項目について、担保しているコードの `ファイル:行` を示す。
3. 各項目について、失敗を検出するテストの名前を示す。**テストが無い項目は不合格**。
4. 仕様に無い実装を見つけたら挙げる（過剰実装も検収の対象）。
5. 検証できない項目（実機が要る等）は「未検証」として分離する。合格にしない。

出力は項目ごとの表。1 項目でも根拠が欠けたら不合格。

## 可読性レビュー

入力: コードだけ。仕様書も実装者の説明も読まない。

次の 8 点で見る。それぞれ「良い例」の基準を満たさない箇所を `ファイル:行` で挙げる。

| # | 観点 | 合格の基準 |
|---|---|---|
| 1 | 名前 | 型・関数・変数が「何であるか」を言っている。`data2`、`tmp`、`res`、`buf1` が無い |
| 2 | 関数の大きさ | 1 関数が 1 つの抽象度。20 行を超えるなら、超える理由が読んで分かる |
| 3 | コメント | 「何を」ではなく「なぜ」。ハードウェア由来の定数には根拠がある |
| 4 | エラー | メッセージだけで次に何をすべきか分かる。`unwrap` の代わりに文脈がある |
| 5 | テスト名 | 仕様の文として読める。`test_offset` ではなく `an_offset_reaches_the_display_string` |
| 6 | 一貫性 | 同じ概念に同じ語。`offset` と `position` を混ぜていない |
| 7 | 公開範囲 | `pub` が最小。外部に出さなくてよい型が `pub` になっていない |
| 8 | モジュール doc | 冒頭 3 行で、そのモジュールが何のためにあるか分かる |

さらに、次の 3 つは**必ず指摘する**。

- 消された安全ゲートの理由（`AGENTS.md` に書かれた「なぜその確認が要るか」）
- テストが通ることだけを目的にしたテスト（実装を写しただけのアサーション）
- 実機で未検証なのに、検証済みと読める書き方

### 出力の形

```text
## 可読性レビュー: <対象>

### Must
1. `crates/m241-core/src/protocol/brom.rs:120` — `let tmp = ...` は何の値か名前から分からない
   → `reserved_bytes` に改名

### Should
...

### Could
...

### 良かった点
（次も同じ判断をしてほしい箇所。遠慮せずに書く）
```

## 統合

2 つの報告を突き合わせて、次を決める。

1. **Must が 1 つでもあればマージしない。**
2. Should は、直すか、直さないなら理由を `docs/dev/` に残す。
3. 2 つのレビューが同じ箇所を別の理由で指したら、**可読性の指摘を優先**して直す。
   仕様検収が通っていても、読めないコードは次の変更で壊れる。

統合で残った Must / Should が、そのまま三段構成の「指摘リスト」になる。修正は
指摘者と別のエージェント、検証は修正者と別のエージェントが行う（冒頭の表）。

レビュー結果は `docs/dev/10-review-log.md` に日付と対象つきで残す。
同じ指摘が 3 回出たら、レビューではなく仕組み（lint、テスト、テンプレート）で塞ぐ。
