# レビュー手順

## 発見 → 修正 → 検証の三段構成

レビューで問題が見つかったとき、**指摘した本人に直させない**。修正は
**指摘したのとは別のエージェント**が行い、その修正は**さらに別のエージェント**が
独立に検証する。三つの段階は、それぞれ別のエージェントが担当する。

| 段階 | 担当 | 入力 | 出力 |
|---|---|---|---|
| 発見 | レビュー担当 | 仕様書・コード・テスト | `ファイル:行` つきの指摘リスト |
| 修正 | 指摘したのとは**別**のエージェント | 指摘リスト | 修正の差分 |
| 検証 | 修正したのとは**別**のエージェント | 指摘リスト、差分、テスト | 合格 / 不合格 |

修正担当は、指摘が事実と違うと思ったら**直さずにそう言う**。黙って従って
誤った変更を入れるより、異論を書いて残すほうがよい。指摘者本人に直させない
理由は、自分が下した判断を同じ前提で読み直してしまうから。検証担当も同じ理由で、
**修正者の説明を読まない**。説明は、悪い修正を言葉で通り抜けさせるための装置になる。

### 検証担当が読むもの

- 指摘リスト（`ファイル:行` と重大度）
- 修正の差分（`git diff` / `git show`）
- テスト（追加・変更されたテストと、その実行結果）

**読まないもの: 修正者の説明。** コミットメッセージの本文も、修正担当が書いた
「なぜこう直したか」の報告も読まない。差分そのものだけを見る。

### 検証の合格条件

3 つすべてを満たしたときだけ合格とする。

1. 指摘がすべて解消している（各指摘の `ファイル:行` に対応する変更が diff にある。
   見送る場合は、見送る理由が指摘リスト側に記録されている）
2. 修正が新たな問題を入れていない（diff に指摘と無関係な変更が無い。
   無関係に見える変更があれば、それが何の指摘に対応するか説明できる）
3. `./tools/check.sh` が 6/6 で通る

1 つでも欠けたら不合格として差し戻す。検証担当は自分で直さない。

## 2 種類のレビュー（発見段階）

実装とは独立した 2 種類のレビューを、**互いの結果を見せずに並行で**走らせる。
片方だけでは足りない理由がある。

| レビュー | 読むもの | 読まないもの | 問い |
|---|---|---|---|
| 仕様検収 | 仕様書、テスト、コード | 実装者の説明 | 仕様の各項目が、コードとテストのどこで担保されているか |
| 可読性レビュー | コードだけ | 仕様書、実装者の説明、仕様検収の結果 | 半年後の他人が、説明なしで読めるか |

## なぜ分けるか

仕様検収だけだと「仕様に合っているから読みやすさは問わない」になる。
可読性レビューだけだと「きれいだが仕様を満たしていない」を見逃す。

そして**仕様書を読ませないことが可読性レビューの条件**である。
仕様を知っていると、コードの不明瞭さを仕様で補って読めてしまい、
初見の読み手が感じる引っかかりが消える。実装者の説明を読ませないのも同じ理由。

## Tier 制（レビューの深さ）

差分の大きさと危険度で、読む範囲を変える。Tier が低くても「著者とは別の
セッション」は必須で、`review-gate` も必要。

**Tier 1 でも `review-gate` status は必須。** Tier で変わるのはレビューの深さだけで、
「著者とは別のセッション」「マージ前の status」はどの Tier でも同じ。

| Tier | 対象 | Stage 1 | Stage 2 | Stage 3 | 変異テスト |
|---|---|---|---|---|---|
| 1 | docs のみ、テストのみ、または非テスト 1–100 行 | 独立レビュアー1本（仕様検収。可読性は n/a） | 必要なら別エージェント | 原則不要。挙動を変えるなら必要 | 挙動変更時のみ |
| 2 | 通常のコード。非テスト 101–300 行、1 つのモジュールに閉じる | 仕様検収 + 可読性の2本。変更ファイルのみ | 別エージェント | 必須 | 3〜5 件 |
| 3 | 安全-critical（`m241-flash`、プロトコル、ジオタグ = EXIF 書き換え、破壊的経路）は行数に関係なく。または非テスト 301 行以上、または複数モジュール横断 | 2本。変更ファイル全体 + 関係する仕様 | 別エージェント | 必須・深掘り | 10 件以上 |

Tier 3 の「関係する仕様」は**仕様検収だけが読む**。可読性レビューはどの Tier でも
仕様書を読まない（上の「2 種類のレビュー」）。

行数は「非テスト行」で数える。テストと docs は行数に含めないが、レビュー対象からは外さない。
数え方の例: `git diff --numstat <base>..HEAD -- ':!**/tests/**' ':!**/*_test.rs'` の
追加行 + 削除行の合計。`#[cfg(test)]` など**ソース内の inline テストは含める**。
迷ったら多めに数え、上の Tier に倒す。

301 行以上の通常コードは、まず PR を分割する。分割できない理由を PR に書き、
そのうえで Tier 3 とする。このルールを入れる前に始まっている大きなブランチ
（`feat/eztour`、CLI の残り、GUI の残り、DA 書き込み実装
[`08-parallel-work.md`](08-parallel-work.md)）は「分割前の既存ブランチ」として
Tier 3 で深くレビューし、次の変更から分割を前提にする。

Tier 3 の例: DA 書き込み、ファーム書き込み、ログ消去、ジオタグ（EXIF 書き換え）。
Tier 1 でも、安全ゲートや実機未検証の主張に触れるなら Tier 2 以上に上げる。

## Review gate（マージ前の機械ゲート）

`main` へのマージ前に、独立レビュアーが **レビューした head SHA** に
`review-gate` status を付ける。branch protection はこの status を必須に
しているため、status のない PR はマージできない。付けるのは **Stage 3 の後、
マージ直前**（Tier 1 はその限りで Stage 3 を省くことがある）。

```bash
python3 tools/review_gate.py <head-sha> --pr <number> \
  --verdict mergeable --tier <1|2|3> \
  --reviewer "<label>" \
  --review-url "<レビュー記録の URL>"
```

- `<head-sha>` は **40 桁の完全な SHA**。短縮 SHA は「full 40-character SHA
  required」で明示的に拒否される。`gh pr view <n> --json headRefOid
  --jq .headRefOid` で取れる。
- `--reviewer` は独立セッションのラベル。`<stage>:<session-id>`
  （例 `stage3:ses_abcdef`）の形にする。著者のアカウント名を含めると
  スクリプトが警告を出す（部分一致なので、`stage3:ses_...` 形式では
  自己レビューを検出できない）。
- `--review-url` は 3 つの役割を兼ねる。**レビューの記録**（PR コメント、
  または [`10-review-log.md`](10-review-log.md) の該当節）であり、status の
  **`target_url`**（status カードのリンク先）であり、`--verdict blocked` の
  ときの**理由の置き場**でもある。ここが空だと、status から根拠に辿れない。
- `--dry-run` は投稿しないが、**`gh` は呼ぶ**。PR の head を読んで SHA を
  照合してから、投稿コマンドをシェルに貼り戻せる形（`shlex.join`）で表示する。
  認証済みの `gh` とネットワークが要る。オフラインの下見はできない。
- status は commit ごと。修正を push したら SHA が変わるので、新しい head を
  レビューして status を付け直すまでマージできない。
- スクリプトが PR から読むキーは `state`（`open` であること）、`head.sha`
  （照合する SHA）、`user.login`（著者警告）の 3 つ。
- 著者のセッションは status を付けない。付けるのは独立レビュアーだけ。
- `--verdict blocked` は `failure` を付ける。理由を `--review-url` に残す。
- 技術的な限界: write 権限があれば status は偽装できる。branch protection が
  強制できるのは status の存在まで。より強くするなら、2 人目のアカウント +
  required approvals、または信頼できる GitHub App の app-scoped check を使う。

## 共通のルール

- レビュー担当は**コードを書き換えない**。指摘だけ返す。
- 2 つのレビューは独立に走らせ、**互いの報告を読む前**に結論を出す。
- 指摘は必ず `ファイル:行` で示す。行が特定できない指摘は「指摘ではない」。
- 重大度は 3 段階。
  - **Must** — 誤動作、データ損失、安全性の後退、仕様違反。マージ前に直す。
  - **Should** — 読み手が誤解する、または保守で事故る。直すか、直さない理由を記録する。
  - **Could** — 好みに近い改善。 backlog に落としてよい。

## 仕様検収

入力: 対象の仕様書（例 `docs/reference/01-da-protocol.md`）、コード、テスト。

1. 仕様書の項目を 1 行ずつ列挙する。
2. 各項目について、担保しているコードの `ファイル:行` を示す。
3. 各項目について、失敗を検出するテストの名前を示す。**テストが無い項目は不合格**。
4. 仕様に無い実装を見つけたら挙げる（過剰実装も検収の対象）。
5. 検証できない項目（実機が要る等）は「未検証」として分離する。合格にしない。

出力は項目ごとの表。1 項目でも根拠が欠けたら不合格。

## 可読性レビュー

入力: コードだけ。仕様書も実装者の説明も読まない。

次の 8 点で見る。それぞれ「良い例」の基準を満たさない箇所を `ファイル:行` で挙げる。

| # | 観点 | 合格の基準 |
|---|---|---|
| 1 | 名前 | 型・関数・変数が「何であるか」を言っている。`data2`、`tmp`、`res`、`buf1` が無い |
| 2 | 関数の大きさ | 1 関数が 1 つの抽象度。20 行を超えるなら、超える理由が読んで分かる |
| 3 | コメント | 「何を」ではなく「なぜ」。ハードウェア由来の定数には根拠がある |
| 4 | エラー | メッセージだけで次に何をすべきか分かる。`unwrap` の代わりに文脈がある |
| 5 | テスト名 | 仕様の文として読める。`test_offset` ではなく `an_offset_reaches_the_display_string` |
| 6 | 一貫性 | 同じ概念に同じ語。`offset` と `position` を混ぜていない |
| 7 | 公開範囲 | `pub` が最小。外部に出さなくてよい型が `pub` になっていない |
| 8 | モジュール doc | 冒頭 3 行で、そのモジュールが何のためにあるか分かる |

さらに、次の 3 つは**必ず指摘する**。

- 消された安全ゲートの理由（`AGENTS.md` に書かれた「なぜその確認が要るか」）
- テストが通ることだけを目的にしたテスト（実装を写しただけのアサーション）
- 実機で未検証なのに、検証済みと読める書き方

### 出力の形

```text
## 可読性レビュー: <対象>

### Must
1. `crates/m241-core/src/protocol/brom.rs:120` — `let tmp = ...` は何の値か名前から分からない
   → `reserved_bytes` に改名

### Should
...

### Could
...

### 良かった点
（次も同じ判断をしてほしい箇所。遠慮せずに書く）
```

## 統合

2 つの報告を突き合わせて、次を決める。

1. **Must が 1 つでもあればマージしない。**
2. Should は、直すか、直さないなら理由を `docs/dev/` に残す。
3. 2 つのレビューが同じ箇所を別の理由で指したら、**可読性の指摘を優先**して直す。
   仕様検収が通っていても、読めないコードは次の変更で壊れる。

統合で残った Must / Should が、そのまま三段構成の「指摘リスト」になる。修正は
指摘者と別のエージェント、検証は修正者と別のエージェントが行う（冒頭の表）。

レビュー結果は `docs/dev/10-review-log.md` に日付と対象つきで残す。
同じ指摘が 3 回出たら、レビューではなく仕組み（lint、テスト、テンプレート）で塞ぐ。
